# 项目章程

## 1. 项目背景

大模型推理的公开性能数据通常来自数据中心 GPU，消费级 12GB 单卡的约束不同：模型权重会占据大部分显存，KV Cache、CUDA Graph 和临时工作区共享剩余空间；并发提升可能增加总吞吐，也可能让排队时间和尾延迟迅速恶化。

Qwen2.5-3B-Instruct 包含 36 层、16 个注意力头和 2 个 KV 头，隐藏维度为 2048，权重数据类型为 BF16。仅权重理论大小约为 `3.09B * 2 bytes ~= 6.18 GB`。在 RTX 5070 12GB 上，它足以运行，却没有可以随意浪费的显存，因此适合研究资源约束下的推理系统行为。

已有 vLLM 提供 continuous batching、chunked prefill、paged KV cache、prefix caching 和 LoRA serving，但“功能存在”不代表对所有负载都有效。本项目要回答这些机制在固定消费级硬件上的收益、代价和适用边界。

## 2. 问题定义

在固定 RTX 5070 12GB、WSL2、Qwen2.5-3B-Instruct 和 vLLM 版本的前提下：

> 如何在满足预先冻结的 TTFT、TPOT、错误率和生成质量约束时，最大化单卡 LLM 服务的 goodput？

其中 goodput 定义为单位时间内同时满足全部 SLO 的成功请求数。原始 requests/s 和 tokens/s 作为辅助指标，不能单独代表服务优化成功。

## 3. 项目目标

- O1：建立显式参数、固定模型 revision、可重复执行的 vLLM BF16 基线。
- O2：建立覆盖 TTFT、TPOT、ITL、E2E、吞吐、goodput、显存和错误率的实验体系。
- O3：得到 batch token budget、并发度、输入输出长度之间的容量和延迟关系。
- O4：定量评估 prefix caching 与 FP8 KV Cache 的收益阈值和质量风险。
- O5：完成 AI Infra 故障诊断领域的 QLoRA 训练、离线评测和 LoRA 在线服务。
- O6：实现 token-aware 的 SLO 准入控制，并在突发与混合长度流量下和固定并发策略比较。
- O7：形成包含原始数据、环境快照、实验脚本、失败实验和适用边界的技术报告。

## 4. 研究问题与假设

| 编号 | 研究问题 | 待验证假设 |
|---|---|---|
| RQ1 | 输入长度和并发度如何改变 prefill、decode 与显存压力？ | 长输入主要放大 TTFT，较高并发主要放大 queue time 与 TPOT 尾延迟。 |
| RQ2 | batch token budget 如何影响延迟和吞吐？ | 较小 budget 有利于 decode 延迟，较大 budget 有利于 prefill 与总吞吐，存在负载相关最优点。 |
| RQ3 | prefix caching 何时值得开启？ | 收益由公共前缀长度和复用率共同决定，对无重复前缀负载收益有限。 |
| RQ4 | FP8 KV Cache 是否值得质量代价？ | 它能提高活跃 token 容量，但整体并发提升小于理论 2 倍，且需要质量校验。 |
| RQ5 | LoRA 的在线代价是多少？ | 3B 模型上的单 Adapter 可控，但并发和 Adapter 切换会产生可测开销。 |
| RQ6 | 自适应准入能否改善过载表现？ | 它不一定提高原始吞吐，但会提高满足 SLO 的 goodput 并限制尾延迟。 |

假设不是结论。报告必须保留被数据否定的假设。

## 5. 系统边界

核心范围：

- 单张 RTX 5070 12GB；
- Windows 11 + WSL2 Ubuntu；
- Qwen2.5-3B-Instruct；
- vLLM 在线推理；
- QLoRA SFT 与 LoRA serving；
- 单实例准入、压测和观测。

当前非目标：

- 全参数训练或预训练；
- 多机、多卡、FSDP、ZeRO 的实际部署；
- Kubernetes、Ray 集群和生产级高可用；
- 用未经测量的百分比包装项目结果；
- 把领域聊天界面作为主要交付。

## 6. 完成标准

项目只有同时满足以下条件才算完成：

1. 新环境能按文档启动受控基线并完成 smoke benchmark。
2. 每个核心研究问题至少有一个控制变量实验和三次有效重复。
3. 原始结果、环境快照、服务参数、模型 revision 和 Git commit 可关联。
4. Base 与 LoRA 使用固定测试集完成质量和在线性能双重比较。
5. 准入控制与无限制、固定并发两种策略在相同请求轨迹上比较。
6. 最终结论包含数值、波动范围、负载条件和不适用边界。
7. README 中的所有核心表格都能由仓库内脚本从原始结果重新生成。

## 7. 阶段计划

| 阶段 | 周期 | 产物 | 退出条件 |
|---|---:|---|---|
| M0 环境基线 | 1 周 | 环境快照、受控启动配置、smoke 结果 | 3B BF16 稳定服务且无 CUDA/OOM 错误 |
| M1 基准体系 | 1 周 | 短中长负载、结果 schema、基础图表 | 三次重复能给出稳定 P50/P95 指标 |
| M2 推理优化 | 2 周 | batch、并发、prefix、FP8 KV 对照 | 回答 RQ1-RQ4，记录失败配置 |
| M3 训练闭环 | 2 周 | 数据卡、QLoRA、质量评测、Adapter | Base/LoRA 的质量和服务成本可比较 |
| M4 系统深化 | 2 周 | 准入控制、突发流量与公平性实验 | 回答 RQ6，给出 goodput 对比 |
| M5 项目收尾 | 1-2 周 | 报告、图表、复现命令、简历描述 | 独立复现实验并通过完成标准审计 |
